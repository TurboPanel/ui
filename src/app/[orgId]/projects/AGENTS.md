# Projects & environments (`/<orgId>/projects/*`) — AGENTS.md

Console-wide rules: `../AGENTS.md`; repo-wide rules: `../../../../AGENTS.md`.

## Primary environment, pinned environments and the Base

A project **opens on its primary environment** (`[projectId]/index.tsx`: the environment with `isPrimary`, else the first listed; the Environments tab only when there is none). `GET /environments` already returns primary first, pinned next, then oldest; `orderEnvironments` in `src/lib/v4/primary-environment.ts` keeps that order. The words are always **primary environment** (never "default environment") and **pinned**. Environment Settings has the **Primary environment** section (Make primary behind a confirmation sheet, `POST /environments/:id/primary`; Pin or Unpin, `PATCH /environments/:id { pinned }`); the primary environment cannot be deleted while others exist (the settings view and the header menu say why, the server answers 409 `primary_environment_cannot_be_deleted`). There is **no "follows the Base" label or flag anywhere**: every environment inherits from the Base, and each service, field, Hosting Account and variable says where its value comes from with the config view's `inheritedFromBase` (the plain tag **From the Base**; a value the environment sets itself reads "{env} change", or "Set in {env}" when it stands alone). Edits on the environment Configuration tab always go to that environment (no "where does this change go" choice); the Base is edited only from the Base tab, whose screens carry the line "Shared defaults for all environments". Every project compose save names its `target` (`base` or an environment id). With two or more environments the Environments header has an **Open the Base** button and a line on when to use it. The New environment sheet starts as **Copy of {primary}** (`start: "copy"`), with **Empty, stands alone** (`start: "empty"`) as the other choice. The new-project screen sends the compose it drafted and the control plane puts it in the primary environment (the Base starts empty); a Compose project then opens **Set up production** (`setup/environment`) for that environment, and from there the environment itself.

## Navigation shell (Compose projects)

A Compose project has **one tab bar of six tabs** (`ProjectPageTabs` in `project-shell.tsx`, ids and labels in `project-navigation.ts`): **Environments** (`/overview`, `project-environments-tab.tsx`: one layer card per environment, primary first (`environment-layer-card.tsx`: a Primary or Pinned badge, running now, last deploy, a mini map, branch, server, "N changes from the Base", "Same as the Base" or "Stands alone"), and, with two or more environments, the Base band, and **New environment** (`new-environment-sheet.tsx`: name, Copy of the primary environment or Empty/stands alone, server). Every part comes from data read (containers, newest deploy, `GET /environments/:id/config-view` through `lib/queries/environment-cards.ts`); a part with no answer is left out, never guessed. The **Projects home** (`/projects`, `components/org/projects-home-section.tsx`) is built the same way: a layer card per project (managed databases included, with a second line saying what each project is), a recent-projects row, deploys in progress, and the **All · Apps · Managed databases** type filter in `?type=`; pure logic in `src/lib/v4/projects-home.ts` and `project-home.ts`), **Base** (`/base`, the shared compose; `/base/storage` lights it too), **Compose** (`/base/compose`; `/base/services`, the Compose editor's Services view, lights it too), **Bindings** (`/base/bindings`), **Hosting** (`/base/hosting`) and **Settings** (`/settings`). An **environment** has **one tab bar of seven tabs** — **Overview** (`/environments/:id`), **Deployments** (`/deployments`, the deploy history, open), **Services** (id `configuration`, `/configuration`; `/configuration/storage` lights it too), **Compose** (`/configuration/compose`), **Bindings** (`/configuration/bindings`), **Hosting** (`/configuration/hosting`) and **Settings** (`/settings`, plus branch and deploy-on-push) — under one header that is identical on every tab (`environment-shell.tsx`, mounted by the `[environmentId]/_layout.tsx`): line 1 is the name (always the environment picker, `ProjectScopePicker` `variant="title"`, whose first row **All environments** goes to the project's Environments tab) with its **Primary** or **Pinned** badge, then **Visit <hostname> ↗** (`visit-site-button.tsx`; a split button listing every public hostname when there are several, "Visit ↗" on a phone, no button without a hostname), **Deploy**, **Restart** (or **Start** when stopped) and the **⋯** menu (previews, cacheless redeploy, Stop, Refresh, environment settings, Destroy, Delete — rules in `src/lib/environment-menu.ts`); line 2 is the status facts (Running now, Last deploy; **Not deployed** only when a real count exists, which the API does not serve yet). Visit opens the **primary hostname**: `environment.options.primaryHostname` while it is still one of the environment's public hostnames, else the oldest (`environmentSiteHostnames` / `primarySiteHostname` in `src/lib/environment-status.ts`); the Hosting tab's **Primary hostname** panel (`primary-hostname-panel.tsx`) sets it with **Make primary**. Environment pages show no "Projects ›" or "All environments ›" crumb: the top bar carries `Projects › project › environment` (plus the page when deeper than a tab), and a phone gets a "‹" back arrow to the project's environments beside the project name. On a phone every tab bar (`UnderlineTabs`) is one row that scrolls sideways with an edge fade and keeps the selected tab in view.

- **One lifecycle model per environment page** (`EnvironmentLifecycleProvider` in `overview-environments-panel.tsx`): the header buttons, the deploy output and confirm sheet under the header, and the Deployments tab all read it. Do not mount a second `useOverviewEnvironmentsPanelModel` — polling doubles and a deploy started in the header would not show its output.
- **Environment Overview** (web, Compose projects; `environment-overview/` under `components/org/project`, mounted by `EnvironmentOverviewScreen`): a problem notice when the newest deploy failed or was rolled back (the control plane's `errorMessage`, first line), the **map** (`environment-map.tsx`, laid out by `src/lib/v4/map-layout.ts`; the stacked form under 768 px; one **Visitors** box per app: its hostnames (each hosting's `options.hostnames`, read with the header's `hostingHostnames`, oldest hosting first; the hosting's name only while it has none) with the primary hostname first, at most two more lines with "+N more", where they are served from (`servedFromOf`: a pinned public address, else the addresses the certificate's DNS check expects (kept only while it waits for DNS), else the organization's public addresses on the environment's server, else the public addresses that server reports itself (`serverPublicAddresses`, read from `useOrgServers`); Datacenter and Local say so; no line when nothing is known), and the worst certificate of its hostnames as a badge on a line of its own; the box grows a line per extra line and takes a second row when it must), the services list, the **Changes from Base (n)** or **stands alone** card and the three latest deploys. The data is assembled in the app (`src/lib/v4/environment-overview.ts`, `overview-deploys.ts`) from the config view (`fetchEnvironmentConfigView` in `src/lib/instance-api.ts`), services, containers, hostings, TLS, storage, bindings, Linux users and deploy history. Services are keyed by their **compose name**, because that is how the config view keys its rows and changes; `recordIds` maps a name to the service record id for links. What the API does not say is left out, never guessed: volume size and last backup, database state, crash counts (no crash notice until the server reports run state), and the certificate word (Unknown unless a pinned certificate row says more). There is **no Add service control**: the platform has no call that adds a service (`createService` is rejected, services come from the compose file). When the config view cannot be read (no manage access, or a saved compose that does not parse) the old compose screen stays. The phone app keeps the old screen until the map has a native layout. The child of `Link asChild` takes one flattened style object (`link-as-child-style.test.ts`).
- **Base tab** (web, Compose projects; `base-tab/` under `components/org/project`, mounted by `ProjectBaseScreen` at `/base`): the **Base map** with Compare with (none or one environment: the comparison is the map's Differences view), the services the Base declares, the project variables (edited here with the Configuration tab's editor: add, change the value and where it is used, remove after a confirm; edits stay staged with Unsaved and Undo until **Save changes**, which writes the project's own variables through `useSaveBaseVariables` and never a compose; the full table, with literal values, descriptions, renaming, presets and the text view, sits under a closed **Advanced** section, saves at once and refreshes the config views through `useRefreshBaseConfiguration`), the Linux users (with the apps that run as each in each environment) and "Environments built from this Base" (how each relates to the Base, a link to its changes). There is no project-level config view: the Base is read from any one environment's config view (`useEnvironmentConfigViews`), and the table uses the same words as the cards (`environmentRelation`). Logic is in `src/lib/v4/project-base.ts`. The Base is not running anywhere, so its map has no run state and nothing opens from a station. When no environment's configuration can be read the old compose screen stays, and the phone app keeps it too, with the project variables (`BaseVariablesSection`) under it. The other `/base/*` routes (`compose`, `services`, `bindings`, `storage`, `hosting`) render `ProjectBaseLensScreen`, the old compose surface; the Compose file editor stays there, linked from the Base tab.
- **Compose projects and managed databases** get this chrome (`useEnvironmentChrome`); a managed database gets its own header (`ManagedEnvironmentHeader`) and greyed tabs, see **Managed projects** below. Platform (system) projects keep `SystemProjectOverviewPanel` (its read-only strip is `SystemEnvironmentPanel`). Create-wizard drafts get lens tabs in the shell (`DraftLensTabs`: Overview · Compose · Services) that switch `draft.section`. A repository project is created straight from the new-project screen, so it has no draft step.
- **Retired paths redirect** (`LegacyProjectRedirect`, table in `legacyProjectRedirectHref`): `/compose`, `/services`, `/bindings`, `/hosting`, `/storage` → under `/base` (project) or `/configuration` (environment); `/servers` → Hosting; `/map` → Overview. The query rides along (`?hostingId=` is a live deep link; `useHostingDeepLink` in the shell opens the Hosting lens for it). A service opens **inside its environment** at `/environments/:environmentId/services/:serviceId` (`EnvironmentServiceScreen` in `service-detail-screen.tsx`, `projectEnvironmentServiceHref`): the environment header, Deploy and the tab bar stay with **Services** lit, a "‹ {environment}" link goes back to the Services tab, and "Edit the Base" opens the Base Services editor for the defaults every environment shares. The old `/services/:serviceId` only redirects there (`ProjectServiceRedirectScreen`: the environment whose service list holds the id, query kept); links that cannot know the environment, such as a database's connected services, still use it. Internal links never go through a redirect: every href builder emits the new paths, and `project-routes.test.ts` reads the route tree to prove each link has a file.
- **Tab bar:** `UnderlineTabs` (`components/ui/v4`) serves the project, environment and organization tabs; pressing a tab navigates with `router.push` to its href (`projectPageTabHref`, `environmentPageTabHref`, `orgSettingsTabHref`).

Managed databases list their environments on the project **Environments** tab (`/overview`, `project-environments-section.tsx`: rename, new environment and the first environment's auto-provision). Compose projects have no Environments section tab — env work lives under the selected environment chip. Hosting, Bindings, Storage, and Settings are compose surface tabs (`ComposeHostingTab` / `ComposeBindingsTab` / `ComposeStorageTab` / `ComposeSettingsTab` in `compose-resource-tabs.tsx`) on both Project and environment scope; the retired Servers tab folded into Hosting (`/servers` paths redirect there). Compose Overview owns the unified chip strip (path `/environments/:id` selects that env).

**Overview Compose panel** (`compose-tabs.tsx` → `ComposeServicesTab` + `overview-environments-panel.tsx`):

- **The compose file is the surface.** The compose editor has **no section nav of its own** — no rail, no second tab strip; the page tab bar is the only one. Overview / Compose / Services are three _representations of one artifact_; **Hosting** is the one operational tab beside them (server placement + exposure, i.e. where the scope runs and how it is reached); Storage is a _property of a service_ and Settings a _property of a scope_, both reached from the object they belong to rather than the bar.
- **One tab bar:** the project and environment tab bars carry Compose, Bindings and Hosting, so the compose surface draws no lens bar of its own. The Base Compose editor keeps a small Compose / Services toggle (`ComposeEditorViewTabs`, routed through `projectComposeEditHref`) because the project bar has no Services tab; that toggle is how `/base/services` is reached. `project-routes.test.ts` lists every route under a project with the tab, redirect or link that reaches it.
- **Services lens — Document view** (`ComposeDocumentView` + pure `src/lib/compose/document-model.ts`): the compose file rendered as YAML-shaped blocks, each service carrying a status dot and a right gutter of live facts (published ports, hostname). Pressing a block expands that service's compose fields inline (the same `ComposeVisualServiceCard` the card list uses); pressing a gutter fact expands **that fact's** editor inline — the hostname fact mounts `EnvironmentDetailBody sections={['hosting']}` narrowed with `filterServiceNames` to the one service. Nothing here navigates. **Detected apps:** a service whose `ServiceRecord.app` is set (the daemon recognised WordPress in its document root; read-only) carries an `app` fact (`WordPress`) in the gutter and replaces the `site` kind tag on the Overview box / phone Stack row. When the environment's bindings (the same read the Overview makes) show no MySQL/MariaDB database — Postgres only, or nothing bound — the row gets a warning `InlineNotice` (`WordPress needs MySQL or MariaDB`). Pure logic in `src/lib/compose/app-facts.ts`: a binding with an unknown engine never warns, and nothing warns while bindings are still loading. It is advice, not a gate (a site may point at an external database), and it is not a compose lint rule because it depends on bindings, not the YAML. Only scanned keys get lines (image/build, ports, volumes, depends_on) and the rest is counted (`+ N more keys`), because the verbatim text is one lens away in Compose. Internally it is the `visual` editor view with `visualMode="document"`, so draft/save/lint/session plumbing is shared with the card list — do **not** build a second compose editor for it.
- **Scope strip**: the document's first row states where the scope deploys plus its counts, with a gear opening scope configuration (`/storage`, `/settings`). Paths: `/overview` (Overview diagram), `/compose`, `/services` (Services lens), `/hosting`, `/storage`, `/settings` (Project); bare `/environments/:id` is the environment Overview, plus the same suffixes. `/map` and `/environments/:id/map` are **retired** and redirect to Overview; `/servers` and `/environments/:id/servers` are **retired** and redirect to Hosting; service detail is `/environments/:id/services/:serviceId` (the project-scope `/services/:serviceId` redirects there). Create-wizard drafts get all three lenses (`DRAFT_COMPOSE_PROJECT_TAB_IDS`). The scope chips are gone: the project tabs and the environment header (name picker) carry that job.
- **Unsaved draft session:** `ComposeDraftProvider` (under `ProjectProvider`) holds per-scope draft YAML + full document (`compose-draft-context.tsx`) so switching Overview ↔ Compose ↔ Services **does not wipe** in-progress edits (route remounts rehydrate from the store). Compose/Services stay dual-bound: YAML edits flush into the shared draft when opening Services; Services form edits update draft + visible YAML for Compose.
- **Overview** (`ComposeSavedView`): single-row inline inventory strip + topology diagram (`ComposeGraphView`) drawn with live deployment facts — per-service hostnames as **hosting** nodes above the service layers, and the effective server placement (env pin, else project default) as a mermaid-subgraph-style **server frame** captioned `SERVER · name` around services/networks/volumes; service cards carry a faint SERVICE / SITE kind tag; optional running-service status when the environment is started. When the draft is dirty, Overview defaults to **Proposed** (unsaved) topology with a **Proposed | Saved** toggle to compare the last save, and a **Save** control in the surface header. Blank compose shows empty state.
- **Compose** / **Services** (`ComposeBasePanel` + `sessionKey`): YAML editor or visual forms. **Discard** and **Save** appear only while dirty (hidden when clean); Save stays briefly as “Saving…” during persist. Discard is two-press (`Discard` → `Discard?`) in the surface header so it cannot grow the 40px chrome; it reseeds the draft from the last saved compose (invalid YAML is dropped). Overview Proposed/Saved uses the same pair. The Services form’s `SourceSection` binds a repository through the shared `git-sources/repository-picker.tsx` (**application → account → repository**), which *attaches* on pick — operators with no application yet are sent to `projectGitSourcesHref` (`/<orgId>/projects/git-sources`), which owns registration and installation.
- **Hosting tab** (`ComposeHostingTab`): where the scope runs and how it is reached — server placement first, then hostnames / ports / TLS via `EnvironmentDetailBody` (`embedded`, `showComposeOverlay={false}`, `sections={['hosting']}`). Project scope leads with **Default project server** (`ProjectServerHeaderControl` / `options.defaultServerId`) then stacks every environment (heading when more than one), each with its **Server** pin panel (`updateEnvironment({ serverId })`, clear inherits the project default) above its hosting rows; environment scope is that env's pin + hosting only. Delete controls live only on the **Settings** tab — no project kind has a header trash. Lifecycle (**Deploy**, **Restart** / **Start**, and the **⋯** menu) lives in the environment header (`EnvironmentLifecycleActions`); **New environment** is on the project's Environments tab. The header carries **no** server pin; when the environment has no server it shows a **No server — set one in Hosting** link (`MissingServerHostingLink`) instead, and when a source-backed service has no system user it shows **No system user — assign one in Bindings** (`MissingPrincipalBindingsLink`) and keeps Deploy / Redeploy disabled (a new project made from a repository seeds its app with an account named after the project, so Deploy starts enabled; the Bindings **Add system user** form, while an app waits for an account, declares the account in the document that holds the app and attaches it when it is the project's only one — `planAccountDeclaration`; the Run as chooser lists Base and environment accounts) (`needsPrincipal` via the pure `unownedPrincipalRequiredServices` in `src/lib/compose/principal-required.ts` — the daemon otherwise *silently skips* those releases: "release skipped … no project principal assigned"). Start / Stop stay available — they only touch existing containers. Status is loaded with one `fetchContainers({ environmentId })` per environment on mount / when the environment-id list changes, and again on explicit **Refresh** or after a tracked command reaches a terminal status — **no auto-poll / `refetchInterval`**.
- **Bindings tab** (`ComposeBindingsTab`): what a service deploys *as* and connects *to* — **System users** first (`ProjectPrincipalsSection`, project-wide: native releases publish into the account's home, and the daemon skips any release with nobody assigned), then **Bound databases** per environment (`EnvironmentBindingsPanel` in `src/components/org/environment-bindings-panel.tsx`, built on `useEnvironmentBindings` + the shared `BindingCard` from `service-bindings-panel.tsx`). Connecting a database stays on the managed cluster's Connect tab; this tab views and severs what is bound. Project scope stacks every environment (heading when more than one); environment scope narrows to it.
- **Environment picker** (`ProjectScopePicker`, now the environment name in the header; pure helpers in `src/lib/project-scope.ts`; the old `ProjectScopeSelector` chip strip was removed): **Project** is always the first control and **never** collapses into the picker. Environments sit to its right — chips while there is at most `PROJECT_SCOPE_CHIP_MAX_ENVIRONMENTS` (1), and `ProjectScopePicker` (`project/project-scope-picker.tsx`) past that: an anchored menu (desktop) / bottom sheet (compact) with a filter field once the list reaches `PROJECT_SCOPE_SEARCH_MIN` (8). The picker trigger always names an environment — the active one, or (on Project scope) the first, rendered **unhighlighted** via `resolveScopeTriggerOption`, so the operator can see what is over there instead of guessing at a blank control. Platform projects place **one environment per server**, so this list grows with the fleet; do **not** answer growth by widening or scrolling the chip strip.
- **Project container status** (`useContainersByProject` in `src/lib/queries/containers.ts`): **one** `GET /containers?projectId=` for the whole project, grouped client-side by the `environmentId` the control plane stamps on each row. It replaced `useContainersByEnvironments`, which issued one request per environment — and, with `observeUntilHostDeployed`, polled that way too, so a platform project's cost scaled with the fleet. Pass memoized `environmentIds` so environments with nothing running still get an empty bucket. Never reintroduce a per-environment fan-out for project-scoped status.
- **Environment labels** (`src/lib/resource-labels.ts`): `environmentDisplayName(env, { servers, preferServer })`. Platform projects name **every** environment after the component (`HTTP/HTTPS Ingress` on each), so `preferServer` (set for system projects) resolves the placed server instead — otherwise every chip renders the same string. Falls back to the environment name until `useOrgServers` resolves. `serverDisplayName` (name → hostname → short id) and `resolveServerLabel` are the single implementation for server labels, and the platform panel's **Target server** uses them rather than printing a raw UUID. Project-editor call sites are migrated; server / managed / datacenter screens still carry local copies — fold those in when you next touch them, never add a new one.
- **Inheriting environments** (`ComposeInheritedPanel`): an environment with a blank overlay renders an `InlineNotice` (**Using project compose** — the copy says "using", never "inheriting" — plus **Create override** / **Start from project compose**) above the project compose shown **plainly and readably** — selectable mono in a recessed `Project compose · read only` block, or compact service rows on the Services tab. Opening **Compose** on an inheriting environment starts a blank overlay. The history row ends as **Cancelled** (failed tone, plain note that nothing changed and the previous version still runs); a deploy that finished anyway shows "Finished before it could be cancelled." - **Environment Settings** (`/environments/:id/settings`, `EnvironmentSettingsBody` in `project/settings/environment-settings-screen.tsx` over the presentational `environment-settings-view.tsx`; pure rules in `src/lib/v4/environment-settings.ts`): the branch and deploy-on-push panel below, the **Server** (where it runs, and **Move to another server** behind a confirmation sheet), the **Name** (rename, checked against the project's other environments, Save only when changed) and the Danger zone (`EnvironmentDeleteControl`). Environment variables live on Configuration, not here. `EnvironmentSettingsPanel` in `project-settings-area.tsx` is now only reachable through the retired compose Settings tab and is to be removed with it.
- **Git branch per environment** (`project/environment-git-source-panel.tsx`, mounted by `EnvironmentGitSourceSection` on the environment **Settings** tab; hidden when no service is bound to a repository): shows the branch each Git-bound service builds in the selected environment (its own override, else the project's, else the repository default) and a **Deploy on push** switch. The repository's own **Auto-deploy** switch still arms the webhook for every environment, so each service says both in one sentence from `src/lib/v4/push-deploy.ts` ("Pushes to live deploy production: off (repository auto-deploy is off)") with **Turn on** for whichever switch is off; Project Settings' Git section says the same sentence per environment. - **Preview Deployment** (`PreviewDeploymentModal` in `src/components/org/project/preview-deployment-modal.tsx`): the header **⋯** menu opens inspect (**Preview merged compose** / **Preview prepared compose**). **Deploy** / **Cacheless redeploy** open confirm (Prepared default) then enqueue. - **Managed engine versions:** operators pick a **version series** (`18`, `9.7`, `12.3`) plus a base-OS **variant** (Alpine / Debian / Oracle Linux 9 / UBI) — never a raw OCI tag. `src/lib/managed-releases.ts` mirrors the control-plane catalog (`turbopanel/src/features/managed/releases.ts`); `MANAGED_SERVICE_CATALOG` `defaultImage` / `allowedImages` derive from it, and `managed-releases.test.ts` pins the literal set. MariaDB **11.8** is the default for new databases; **12.3** stays tested/creatable but `failoverCapable` is false (`managedSeriesFailoverSupport` — single server until automatic failover supports it; **422** `managed_failover_unsupported`). `ManagedVersionPicker` (`managed/managed-version-picker.tsx`) is the **only** place a series is chosen: it appears on the managed setup panel and sends `engineSeries` / `imageVariant`. A cluster's series is immutable afterwards (**409** `managed_series_immutable`), so the Settings panel's base-image picker offers only other variants of the running series (`managedVariantImagesForImage`); for PostgreSQL the control plane also refuses an Alpine <-> Debian swap (**409** `managed_variant_swap_unsafe`, text indexes would break), and the picker still offers it, so the refusal surfaces through `managedErrorMessage` and the Status header shows `PostgreSQL 18 · Alpine` from `detail.release` (`managedReleaseSummary`). Adding a series is a three-repo change — control-plane catalog, daemon allowlist, this mirror.
- **Managed external access:** one yes/no per **server**, "Allow external access to the databases on this server" (default No), not a per-cluster scope menu. No = only services on that server connect (sites run by a site owner's Linux user on `127.0.0.1`, containers bound to the cluster over the managed Docker network); Yes = the database ports are open on all of the server's addresses and the firewall decides who reaches them (keep that safety fact in the hint); while Yes, the settings panel's switch (`addresses` prop) links to the Network tab's **Addresses clients use** card; `ServerAddressesLink` renders nothing when the card would be hidden (older control plane, or no manage). Always show the plain warning when `otherClusters > 0` (the switch moves those too). Endpoints use `reach: 'local' | 'external'`; never show raw scope values or network names. Newer control planes label external endpoints and send `connections[]`: the Connect panel then shows one copyable string per address, labelled `Public: <host>` / `Datacenter <name>: <host>` (`connectionStringLabel`), main first and marked **(main)** from the entry's `primary` flag (not its position), each copy button named by its address, and keeps the single DSN when the list is absent. `addressNeeded` shows **Set the address clients use** with a link to the server's Network tab.

It is a **client-facing** policy at the shared ProxySQL listener; the listener ↔ engine leg is always encrypted, so never present this as "turn on database TLS". `ManagedSettings.ssl` is `{ mode?: ManagedSslMode }` — **omitting `mode` is what keeps a service inheriting**, so the settings form must send `{}` rather than the resolved value. `ManagedSslModePicker` (`managed/managed-ssl-mode-picker.tsx`) is the only picker: it renders the inherit row only when given an `inheritLabel` (`managedSslInheritLabel(orgDefault)` → e.g. `Organization default (Require)`). Per-service selection lives in `ManagedSettingsPanel` (`organizationSslMode` comes from detail `ssl.organizationDefault`); org-wide default lives at `/<orgId>/managed/settings` (`ManagedDefaultsSettingsSection`, manage-gated), which invalidates `queryKeys.org(orgId).managed.all` on save because every managed detail response carries a resolved `ssl` block. The Connect panel renders the effective policy from `describeManagedSslPolicy` (DSN parameter · plaintext refused/allowed · which layer set it) and points at the org CA download when the mode verifies — never a hardcoded `sslmode=verify-full` line. **Minimum under external access: `require`.** While any server serving the database has external access on (detail `externalAccess.servers[].enabled`), `ManagedSettingsPanel` passes `weakModesDisabledReason` (`MANAGED_SSL_EXTERNAL_ACCESS_REASON`) and `inheritMode`, so the picker disables `disable` / `allow` / `prefer` (`isWeakManagedSslMode`) and an inherit row that resolves to one of them. The control plane enforces it regardless: 409 `managed_ssl_external_access_minimum` (service mode), `managed_ssl_default_external_access_minimum` (org default; the defaults API carries no external-access facts, so that section only shows the refusal) and `external_access_weak_ssl` (turning the server switch on). All three are in `SERVER_NAMED_ERROR_CODES`, so `managedErrorMessage` / `managedNamedErrorMessage` show the server's sentence with the server or database names. Data that is still weak under external access is shown raised: detail `ssl.raisedForExternalAccess` makes `effective` `require`, and `describeManagedSslPolicy` names the source `raised to require because external access is on` on the Connect panel.
- **Managed listener ports:** `src/lib/managed-ingress-ports.ts` mirrors the control-plane contract (`turbopanel/src/features/managed/ingress-ports.ts`) — `postgres` / `mysqlFamily` (MariaDB rides the MySQL listener), platform defaults `15432` / `13306`, and the same rejections (`out_of_range` outside `1024`–`65535`, `reserved_admin` `6032` / `6132`, `reserved_private_range` `45000`–`45999`, `collision` when both families match), pinned by `managed-ingress-ports.test.ts`. `managed-services.ts` re-exports `managedIngressPortForEngine` — there must be exactly one implementation. Client-side validation is a courtesy — a **host** listener conflict is only detectable on the server, so a save can still fail from the daemon preflight. **The console reads the authored shape, and only the authored shape.** The instance compiler names its stages — `ComposeLayer[]` (authored) → `Application` → `ResolvedApplication` → `ServerDeployment` (`turbopanel/src/features/compose/ir.ts`) — but the editor, the visual service cards, the document lens, the topology diagram, and the `ui/src/lib/compose/*` lint and merge mirrors all read **stage one**: the `ComposeDocument` as an operator wrote it, plus the `x-turbopanel` blocks that document declares. Nothing in the console models the later three stages, and nothing should start to: placement, container names, slot addresses, release trees and `principal.id`s are compiler decisions the console *displays* (from live facts and from the Prepared preview) rather than derives. This naming pass changed no console behavior and no payload the console reads.
