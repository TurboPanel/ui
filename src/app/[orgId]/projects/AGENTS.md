# Projects & environments (`/<orgId>/projects/*`) — AGENTS.md

Console-wide rules: `../AGENTS.md`; repo-wide rules: `../../../../AGENTS.md`.

## Navigation shell (Compose projects)

A Compose project has **three tabs** (`ProjectPageTabs` in `project-shell.tsx`, ids and labels in `project-navigation.ts`): **Environments** (`/overview`, `project-environments-tab.tsx`: the Base band, then one layer card per environment (`environment-layer-card.tsx`: running now, last deploy, a mini map, branch, server, "Follows the Base · N changes" or "Stands alone"), and **New environment** (`new-environment-sheet.tsx`: name, start from the Base or empty/stands alone, server; there is no copy-another-environment choice because the API has no copy call). Every part comes from data read (containers, newest deploy, `GET /environments/:id/config-view` through `lib/queries/environment-cards.ts`); a part with no answer is left out, never guessed. The **Projects home** (`/projects`, `components/org/projects-home-section.tsx`) is built the same way: a layer card per project, a recent-projects row, deploys in progress; pure logic in `src/lib/v4/projects-home.ts` and `project-home.ts`), **Base** (`/base`, the shared compose; lens routes `/base/compose`, `/base/services`, `/base/hosting`, `/base/bindings`, `/base/storage`) and **Settings** (`/settings`). An **environment** has **four tabs** — **Overview** (`/environments/:id`), **Deployments** (`/deployments`, the deploy history, open), **Configuration** (`/configuration`, lenses `/configuration/compose|hosting|bindings|storage`) and **Settings** (`/settings`, plus branch and deploy-on-push) — under one header that is identical on every tab (`environment-shell.tsx`, mounted by the `[environmentId]/_layout.tsx`): name (a picker when there are several), site link, status facts (Running now, Last deploy; **Not deployed** only when a real count exists, which the API does not serve yet), **Deploy**, **Restart** (or **Start** when stopped) and the **⋯** menu (previews, cacheless redeploy, Stop, Refresh, environment settings, Destroy, Delete — rules in `src/lib/environment-menu.ts`).

- **One lifecycle model per environment page** (`EnvironmentLifecycleProvider` in `overview-environments-panel.tsx`): the header buttons, the deploy output and confirm sheet under the header, and the Deployments tab all read it. Do not mount a second `useOverviewEnvironmentsPanelModel` — polling doubles and a deploy started in the header would not show its output.
- **Environment Overview** (web, Compose projects; `environment-overview/` under `components/org/project`, mounted by `EnvironmentOverviewScreen`): a problem notice when the newest deploy failed or was rolled back (the control plane's `errorMessage`, first line), the **map** (`environment-map.tsx`, laid out by `src/lib/v4/map-layout.ts`; the stacked form under 768 px), the services list, the **Changes from Base (n)** or **stands alone** card and the three latest deploys. The data is assembled in the app (`src/lib/v4/environment-overview.ts`, `overview-deploys.ts`) from the config view (`fetchEnvironmentConfigView` in `src/lib/instance-api.ts`), services, containers, hostings, TLS, storage, bindings, Linux users and deploy history. Services are keyed by their **compose name**, because that is how the config view keys its rows and changes; `recordIds` maps a name to the service record id for links. What the API does not say is left out, never guessed: volume size and last backup, database state, crash counts (no crash notice until the server reports run state), and the certificate word (Unknown unless a pinned certificate row says more). There is **no Add service control**: the platform has no call that adds a service (`createService` is rejected, services come from the compose file). When the config view cannot be read (no manage access, or a saved compose that does not parse) the old compose screen stays. The phone app keeps the old screen until the map has a native layout. The child of `Link asChild` takes one flattened style object (`link-as-child-style.test.ts`).
- **Base tab** (web, Compose projects; `base-tab/` under `components/org/project`, mounted by `ProjectBaseScreen` at `/base`): the **Base map** with Compare with (none or one environment: the comparison is the map's Differences view), the services the Base declares, the project variables, the Linux users (with the apps that run as each in each environment) and "Environments built from this Base" (how each relates to the Base, a link to its changes). There is no project-level config view: the Base is read from any one environment's config view (`useEnvironmentConfigViews`), and the table uses the same words as the cards (`environmentRelation`). Logic is in `src/lib/v4/project-base.ts`. The Base is not running anywhere, so its map has no run state and nothing opens from a station. When no environment's configuration can be read the old compose screen stays, and the phone app keeps it too. The other `/base/*` routes (`compose`, `services`, `bindings`, `storage`, `hosting`) render `ProjectBaseLensScreen`, the old compose surface; the Compose file editor stays there, linked from the Base tab.
- **Only Compose projects** get this chrome (`useEnvironmentChrome`). Managed projects keep `ManagedSectionTabs` and their routes; platform (system) projects keep `SystemProjectOverviewPanel` (its read-only strip is `SystemEnvironmentPanel`). Create-wizard drafts keep the in-memory surface nav.
- **Retired paths redirect** (`LegacyProjectRedirect`, table in `legacyProjectRedirectHref`): `/compose`, `/services`, `/bindings`, `/hosting`, `/storage` → under `/base` (project) or `/configuration` (environment); `/servers` → Hosting; `/map` → Overview. The query rides along (`?hostingId=` is a live deep link; `useHostingDeepLink` in the shell opens the Hosting lens for it). `/services/:serviceId` is unchanged. Internal links never go through a redirect: every href builder emits the new paths, and `project-routes.test.ts` reads the route tree to prove each link has a file.
- **Tab bar:** `UnderlineTabs` (`components/ui/v4`) serves the project, environment and organization tabs; pressing a tab navigates with `router.push` to its href (`projectPageTabHref`, `environmentPageTabHref`, `orgSettingsTabHref`).

Managed environments use the shell **Environments** tab (`project-environments-section.tsx`). Compose projects have no Environments section tab — env work lives under the selected environment chip. Hosting, Bindings, Storage, and Settings are compose surface tabs (`ComposeHostingTab` / `ComposeBindingsTab` / `ComposeStorageTab` / `ComposeSettingsTab` in `compose-resource-tabs.tsx`) on both Project and environment scope; the retired Servers tab folded into Hosting (`/servers` paths redirect there). The shell environment selector keeps the active environment across managed non-Overview tabs; compose Overview owns the unified chip strip (path `/environments/:id` selects that env).

**Overview Compose panel** (`compose-tabs.tsx` → `ComposeServicesTab` + `overview-environments-panel.tsx`):

- **The compose file is the surface.** The project editor has **no wide section nav** — no rail, no seven-tab strip. Overview / Compose / Services are three *representations of one artifact*; **Hosting** is the one operational tab beside them (server placement + exposure, i.e. where the scope runs and how it is reached); Storage is a *property of a service* and Settings a *property of a scope*, both reached from the object they belong to rather than the bar.
- **Surface nav** (`ComposeSurfaceNav` in `project/compose-surface-nav.tsx`, ids in `COMPOSE_PROJECT_SURFACE_TAB_IDS`): a five-item segmented control — **Overview** (`/overview`, the topology diagram), **Compose** (`/compose`, YAML), **Services** (`/services`, service cards), **Bindings** (`/bindings`), **Hosting** (`/hosting`) — that stays five items however much the project grows. An off-bar route (Storage, Settings) keeps Services lit, because those are configuration reached *from* a service row. `ComposeEditorChrome` takes it as `nav` and renders it in the header strip beside the toolbar actions.
- **Services lens — Document view** (`ComposeDocumentView` + pure `src/lib/compose/document-model.ts`): the compose file rendered as YAML-shaped blocks, each service carrying a status dot and a right gutter of live facts (published ports, hostname). Pressing a block expands that service's compose fields inline (the same `ComposeVisualServiceCard` the card list uses); pressing a gutter fact expands **that fact's** editor inline — the hostname fact mounts `EnvironmentDetailBody sections={['hosting']}` narrowed with `filterServiceNames` to the one service. Nothing here navigates. **Detected apps:** a service whose `ServiceRecord.app` is set (the daemon recognised WordPress in its document root; read-only) carries an `app` fact (`WordPress`) in the gutter and replaces the `site` kind tag on the Overview box / phone Stack row. When the environment's bindings (the same read the Overview makes) show no MySQL/MariaDB database — Postgres only, or nothing bound — the row gets a warning `InlineNotice` (`WordPress needs MySQL or MariaDB`). Pure logic in `src/lib/compose/app-facts.ts`: a binding with an unknown engine never warns, and nothing warns while bindings are still loading. It is advice, not a gate (a site may point at an external database), and it is not a compose lint rule because it depends on bindings, not the YAML. Only scanned keys get lines (image/build, ports, volumes, depends_on) and the rest is counted (`+ N more keys`), because the verbatim text is one lens away in Compose. Internally it is the `visual` editor view with `visualMode="document"`, so draft/save/lint/session plumbing is shared with the card list — do **not** build a second compose editor for it.
- **Scope strip**: the document's first row states where the scope deploys plus its counts, with a gear opening scope configuration (`/storage`, `/settings`). Paths: `/overview` (Overview diagram), `/compose`, `/services` (Services lens), `/hosting`, `/storage`, `/settings` (Project); bare `/environments/:id` is the environment Overview, plus the same suffixes. `/map` and `/environments/:id/map` are **retired** and redirect to Overview; `/servers` and `/environments/:id/servers` are **retired** and redirect to Hosting; service detail stays at `/services/:serviceId`. Create-wizard drafts get all three lenses (`DRAFT_COMPOSE_PROJECT_TAB_IDS`). The scope chips are gone: the project tabs and the environment header (name picker) carry that job.
- **Unsaved draft session:** `ComposeDraftProvider` (under `ProjectProvider`) holds per-scope draft YAML + full document (`compose-draft-context.tsx`) so switching Overview ↔ Compose ↔ Services **does not wipe** in-progress edits (route remounts rehydrate from the store). Compose/Services stay dual-bound: YAML edits flush into the shared draft when opening Services; Services form edits update draft + visible YAML for Compose.
- **Overview** (`ComposeSavedView`): single-row inline inventory strip + topology diagram (`ComposeGraphView`) drawn with live deployment facts — per-service hostnames as **hosting** nodes above the service layers, and the effective server placement (env pin, else project default) as a mermaid-subgraph-style **server frame** captioned `SERVER · name` around services/networks/volumes; service cards carry a faint SERVICE / SITE kind tag; optional running-service status when the environment is started. When the draft is dirty, Overview defaults to **Proposed** (unsaved) topology with a **Proposed | Saved** toggle to compare the last save, and a **Save** control in the surface header. Blank compose shows empty state.
- **Compose** / **Services** (`ComposeBasePanel` + `sessionKey`): YAML editor or visual forms. **Discard** and **Save** appear only while dirty (hidden when clean); Save stays briefly as “Saving…” during persist. Discard is two-press (`Discard` → `Discard?`) in the surface header so it cannot grow the 40px chrome; it reseeds the draft from the last saved compose (invalid YAML is dropped). Overview Proposed/Saved uses the same pair. The Services form’s `SourceSection` binds a repository through the shared `git-sources/repository-picker.tsx` (**application → account → repository**), which *attaches* on pick — operators with no application yet are sent to `projectGitSourcesHref` (`/<orgId>/projects/git-sources`), which owns registration and installation.
- **Hosting tab** (`ComposeHostingTab`): where the scope runs and how it is reached — server placement first, then hostnames / ports / TLS via `EnvironmentDetailBody` (`embedded`, `showComposeOverlay={false}`, `sections={['hosting']}`). Project scope leads with **Default project server** (`ProjectServerHeaderControl` / `options.defaultServerId`) then stacks every environment (heading when more than one), each with its **Server** pin panel (`updateEnvironment({ serverId })`, clear inherits the project default) above its hosting rows; environment scope is that env's pin + hosting only. Delete controls live only on the **Settings** tab — compose projects have **no** header trash (managed projects keep the header trash). Lifecycle (**Deploy**, **Restart** / **Start**, and the **⋯** menu) lives in the environment header (`EnvironmentLifecycleActions`); **New environment** is on the project's Environments tab. The header carries **no** server pin; when the environment has no server it shows a **No server — set one in Hosting** link (`MissingServerHostingLink`) instead, and when a source-backed service has no system user it shows **No system user — assign one in Bindings** (`MissingPrincipalBindingsLink`) and keeps Deploy / Redeploy disabled (`needsPrincipal` via the pure `unownedPrincipalRequiredServices` in `src/lib/compose/principal-required.ts` — the daemon otherwise *silently skips* those releases: "release skipped … no project principal assigned"). Start / Stop stay available — they only touch existing containers. Status is loaded with one `fetchContainers({ environmentId })` per environment on mount / when the environment-id list changes, and again on explicit **Refresh** or after a tracked command reaches a terminal status — **no auto-poll / `refetchInterval`**.
- **Bindings tab** (`ComposeBindingsTab`): what a service deploys *as* and connects *to* — **System users** first (`ProjectPrincipalsSection`, project-wide: native releases publish into the account's home, and the daemon skips any release with nobody assigned), then **Bound databases** per environment (`EnvironmentBindingsPanel` in `src/components/org/environment-bindings-panel.tsx`, built on `useEnvironmentBindings` + the shared `BindingCard` from `service-bindings-panel.tsx`). Connecting a database stays on the managed cluster's Connect tab; this tab views and severs what is bound. Project scope stacks every environment (heading when more than one); environment scope narrows to it.
- **Environment picker** (`ProjectScopePicker`, now the environment name in the header; pure helpers in `src/lib/project-scope.ts`; the old `ProjectScopeSelector` chip strip was removed): **Project** is always the first control and **never** collapses into the picker. Environments sit to its right — chips while there is at most `PROJECT_SCOPE_CHIP_MAX_ENVIRONMENTS` (1), and `ProjectScopePicker` (`project/project-scope-picker.tsx`) past that: an anchored menu (desktop) / bottom sheet (compact) with a filter field once the list reaches `PROJECT_SCOPE_SEARCH_MIN` (8). The picker trigger always names an environment — the active one, or (on Project scope) the first, rendered **unhighlighted** via `resolveScopeTriggerOption`, so the operator can see what is over there instead of guessing at a blank control. Platform projects place **one environment per server**, so this list grows with the fleet; do **not** answer growth by widening or scrolling the chip strip.
- **Project container status** (`useContainersByProject` in `src/lib/queries/containers.ts`): **one** `GET /containers?projectId=` for the whole project, grouped client-side by the `environmentId` the control plane stamps on each row. It replaced `useContainersByEnvironments`, which issued one request per environment — and, with `observeUntilHostDeployed`, polled that way too, so a platform project's cost scaled with the fleet. Pass memoized `environmentIds` so environments with nothing running still get an empty bucket. Never reintroduce a per-environment fan-out for project-scoped status.
- **Environment labels** (`src/lib/resource-labels.ts`): `environmentDisplayName(env, { servers, preferServer })`. Platform projects name **every** environment after the component (`HTTP/HTTPS Ingress` on each), so `preferServer` (set for system projects) resolves the placed server instead — otherwise every chip renders the same string. Falls back to the environment name until `useOrgServers` resolves. `serverDisplayName` (name → hostname → short id) and `resolveServerLabel` are the single implementation for server labels, and the platform panel's **Target server** uses them rather than printing a raw UUID. Project-editor call sites are migrated; server / managed / datacenter screens still carry local copies — fold those in when you next touch them, never add a new one.
- **Inheriting environments** (`ComposeInheritedPanel`): an environment with a blank overlay renders an `InlineNotice` (**Using project compose** — the copy says "using", never "inheriting" — plus **Create override** / **Start from project compose**) above the project compose shown **plainly and readably** — selectable mono in a recessed `Project compose · read only` block, or compact service rows on the Services tab. It is **not** a card over a dimmed backdrop: the screen exists to show what currently deploys, and a scrim made that unreadable. Overview states the same thing with a quiet **Using project compose** caption at the end of the inline counts row (plain muted text, not an `InlineNotice`).
- **Scope banner** (`ComposeScopeBanner` in `src/components/org/project/compose-scope-banner.tsx`): **Project** scope and **inheriting** environments have no banner. Opening **Compose** on an inheriting environment starts a blank overlay. Banner appears only when the environment has overrides (**Clear overrides**, two-press).
- **Cancel a running deploy** (`RunningDeployNotice` in `project/environment-deployment-history-panel.tsx`, above the history list on the Deployments tab and on the platform strip): while a deploy is still going, a notice offers **Cancel deploy** (two-step `ConfirmButton`, "Keep deploying" backs out; shown only when `canManage`). Once `cancelRequestedAt` is set it reads **Cancelling…** with no button. The history row ends as **Cancelled** (failed tone, plain note that nothing changed and the previous version still runs); a deploy that finished anyway shows "Finished before it could be cancelled." Refusals: `deploy_not_cancellable` / `cancel_unsupported` map in `user-error.ts`. Helpers: `src/lib/deployment-history.ts`. Replace/Wait for a queued deploy is not built yet.
- **Environment Settings** (`/environments/:id/settings`, `EnvironmentSettingsBody` in `project/settings/environment-settings-screen.tsx` over the presentational `environment-settings-view.tsx`; pure rules in `src/lib/v4/environment-settings.ts`): the branch and deploy-on-push panel below, the **Server** (where it runs, and **Move to another server** behind a confirmation sheet), the **Name** (rename, checked against the project's other environments, Save only when changed) and the Danger zone (`EnvironmentDeleteControl`). A move is only `PATCH /environments/:id { serverId }`: the control plane records the pin and does nothing else, so the sheet says exactly that (it changes where the next deploy runs; nothing is copied or stopped). **Not built on purpose:** a "Follows the Base" / "stands alone" switch (the owner finds the label confusing: an environment is always the Base plus its changes; what it changes is read and edited on Configuration), and deploy order and timing (the API does not serve them). Environment variables live on Configuration, not here. `EnvironmentSettingsPanel` in `project-settings-area.tsx` is now only reachable through the retired compose Settings tab and is to be removed with it.
- **Git branch per environment** (`project/environment-git-source-panel.tsx`, mounted by `EnvironmentGitSourceSection` on the environment **Settings** tab; hidden when no service is bound to a repository): shows the branch each Git-bound service builds in the selected environment (its own override, else the project's, else the repository default) and a **Deploy on push** switch. Saving writes the smallest overlay into the environment's compose through `usePersistEnvironmentCompose` (`src/lib/compose/environment-source-branch.ts`): `source.branch` / `source.deployOnPush: false` plus only the markers that let an overlay service save without an image — the merged `serviceKind` (`site` / `node`) or `buildKind: railpack`. A plain image service is shown read-only with the reason. An override equal to the project's is removed, and an overlay service holding nothing else goes with it. The repository's own **Auto-deploy** switch still arms the webhook for every environment, so the panel surfaces it (with a **Turn on** button) when it is off. A push-triggered deploy shows **Push to `<branch>`** and the short commit in the history's Actor column (`trigger` on the history entry). Instance side: `turbopanel/src/webhook/AGENTS.md` ("Which environments a push deploys").
- **Project vs environment selection:** the Base tab (`/base`) is the Project compose, the Environments tab is `/overview` (no query). Selecting an environment chip navigates to `/environments/:environmentId` (or `…/compose` / `…/services` / `…/hosting` if already on those tabs). Post-setup navigation opens `/overview`. The Project Hosting tab lists every environment; environment chips narrow to that env. Context may still keep a concrete `selectedEnvironmentId` under Project scope. Project mode hides lifecycle actions.
- **Preview Deployment** (`PreviewDeploymentModal` in `src/components/org/project/preview-deployment-modal.tsx`): the header **⋯** menu opens inspect (**Preview merged compose** / **Preview prepared compose**). **Deploy** / **Cacheless redeploy** open confirm (Prepared default) then enqueue. Not shown for project-level compose editing or lifecycle Start/Stop. Titles **Compose Preview** vs **Confirm Deployment**. **Merged** — `mergeComposeOverlay(project, environment)` with service `x-turbopanel` kept for audit, plus the live environment pin as `x-turbopanel.placement` (stored compose still never holds placement); **Prepared** — `useDeployPreview` fetch-on-open (no auto-poll). Confirm enqueues deploy (`confirmLabel` matches Deploy / Redeploy / Cacheless redeploy). The Prepared view (`deploy-preview-panel.tsx`) shows the compiled runtime `compose.yaml` (`role: 'runtime'`) the daemon writes on the host — including `x-turbopanel.placement.server_id` — plus `.env` (non-secrets) and `secretPlan[]` file paths, plus one YAML block per `preview.servers[]` **only when the plan spans more than one host** — not a project/environment/platform `-f` chain. Older layer roles may still appear in the payload and must not be presented as what the daemon runs. `ui/src/lib/compose/service-kind.ts` also mirrors the inert per-service **`x-turbopanel.source`** block (`{ sourceId, branch?, subdirectory?, buildCommand?, startCommand?, outputDirectory? }`) and the third **`serviceKind: node`** kind with its `framework` (`auto`/`node`/`next`) and `nodeVersion` hints, plus the `runtime` (`node`/`deno`) and `denoVersion` pair that moves a native service onto Deno (the Services form's **Runtime** chips swap the Node framework and version pickers for a Deno version picker, and the linter mirrors the instance rule that keeps the two runtimes' hints apart) — inert here too, but `node` joins `site` in the editor's image/build exemption (`isHostNativeServiceKind`, also used by `hiddenSiteServiceNames` so a hidden extension does not make the editor flag every native app). `ui/src/lib/compose/lint.ts` mirrors the source block's two rules — a non-blocking "has no effect yet" advisory plus a blocking unresolvable-`sourceId` error that only fires when the caller supplies `knownSourceIds`; the authoritative resolution check runs on the instance write boundary (`turbopanel/src/features/compose/AGENTS.md`). `ui/src/lib/compose/index.ts` mirrors instance merge semantics for the client-side **Merged compose** view; the instance's `turbopanel/src/features/compose/merge.ts` remains the single source of truth for Compose Spec merge behavior (sequence append/dedup rules, `!reset`/`!override` tags, full-replace attributes) — keep the two in sync when merge rules change.
- **Settings tab** (`ComposeSettingsTab` → `ProjectSettingsScreen` / `EnvironmentSettingsPanel` in `src/components/org/project-settings-area.tsx`): scope configuration renders **inline in the surface**, never a dropdown or modal — Settings is a tab at project and environment level. **Project scope:** a quiet **Add Variable** chip plus Workspace, container naming, and Danger → Delete project (`ProjectDeletePanel`); **System users moved to the Bindings tab**. Container naming is a single **Keep original container names** toggle (default Off = rename to service UUIDs; On = `options.containerNaming: 'custom'`) with a warning that keeping names disables rolling updates. **Environment scope:** an **Add Variable** chip for environment-scoped overrides plus Danger → Delete environment (two-press `useDeleteEnvironment`; disabled with a pointer to Project → Settings when only one environment exists). `?hostingId=` on an environment path opens the **Hosting** tab (keeps `?hostingId=` so `EnvironmentDetailBody` can focus the row).
- **Project Settings** (`/settings`, `project/settings/project-settings-screen.tsx` over the presentational `project-settings-view.tsx`; the pure rules are in `src/lib/v4/project-settings.ts`): General (name and description, saved only when changed; the Project ID), Workspace move, Variables (the project's own, kept here until the Base tab takes them), Container names, Git (the repository and when a push deploys, read from the repository list; left out for a project with no repository) with a link to Repositories, "As Compose files" (link to the Base compose file) and a Danger zone (`ProjectDeletePanel`, owners only). **Not drawn because the API does not serve it:** webhook deliveries, project alerts, project members, deploy timing defaults. Platform and managed projects have no such tab and redirect to Overview.
- **Storage tab** (`ComposeStorageTab`): persistent volumes for the active scope via `EnvironmentDetailBody` `sections={['storage']}` (same body as the Hosting tab, so placement resolution and manage-gating are shared). Storage always belongs to an environment (it is provisioned on that environment's server), so Project scope stacks one panel per environment (heading when more than one) and environment scope edits that environment only — there is no project-level store.
- **Deploy / Restart / Start / ⋯** — quiet header buttons (not large primary chips). **Deploy** opens **Confirm Deployment** (a redeploy when something is already deployed) then `deployEnvironment` (optional `{ noCache: true }` for **Cacheless redeploy** in the menu). **Restart** shows while running and calls `runEnvironmentLifecycle(id, 'restart')`; **Start** shows when deployed-but-stopped (`'start'`); neither opens the preview modal. The menu also holds the previews, **Stop** (keeps files/data) and **Refresh status**. Destroy is two-press confirm (`stopEnvironment`) and removes containers **and their data volumes**. Deploy ack conflicts surface plain-language copy.
- **Delete** — compose **Settings tab → Danger** (`organization:own`): with more than one environment, two-press confirm deletes the selected environment; project delete uses `ProjectDeletePanel`. Managed projects keep the header trash control. Name validation via `validateEnvironmentName` for Add.
- Lifecycle / deploy / destroy commands share a **single** `COMMAND_POLL_MS` timer (`useEnvironmentCommands`), never one timer per environment.

- `ProjectEnvironmentsSection` loads `fetchVisibleEnvironments(projectId)` and renders one active environment at a time.
- **Tabs** (`EnvironmentTabs`) only render when there is **more than one** environment; with a single environment the tab bar is hidden and the active environment name shows in the toolbar.
- **Default environment:** when a project has zero environments and the viewer has `organization:own`, the section auto-provisions a single environment named from the org default (`fetchOrgDefaultEnvironment`, falling back to `production`) (once per project, guarded by a `useRef` so React StrictMode's double effect invocation does not create duplicates). The managed auto-provision path uses the same org default. Non-owners just see an empty-state message.
- **Rename** (`updateEnvironment(id, { name })`), **New environment** (`createEnvironment`), and **Delete** (`deleteEnvironment`, two-press confirm, hidden when only one environment remains) are all inline in the toolbar and gated by `organization:own` (display hint; server enforces 403).
- The active environment renders `EnvironmentDetailBody` (exported from `environment-detail-section.tsx`) with `embedded` set, which hides the redundant "Environment" meta panel but keeps merged runtime compose (includes service `x-turbopanel`), the header **⋯** previews + **Deploy** (inspect vs confirm via `PreviewDeploymentModal` — not an always-visible preview panel), hostnames + TLS + **bind** (`public` / `datacenter` / `local`) + optional public **`ipId`** picker (when bind is public), **per-hosting variables** (embedded `VariablesSection` with `{ hostingId }` after the hosting row is saved), **container status**, and environment-scoped variables. The compose Hosting tab uses the same body with `sections={['hosting']}` and `showComposeOverlay={false}` — environment overlays are edited on the surface **Compose** / **Services** tabs at `/environments/:id/compose` (and `/services`); **Clear overrides** only when overrides exist. Switching tabs remounts the body via `key={environmentId}`. Compose projects expose **Keep original container names** (`options.containerNaming`: `uuid` default vs `custom`) on the Project-scope **Settings** tab.
- **Reaching Settings / Delete environment (compose):** Settings is on no nav bar, so it is a tab (project and environment) and the environment header's **⋯** menu holds **Environment settings**, **Destroy** and **Delete environment…** (inline two-press confirm; refused-while-running shows the server message plus a **Stop** button; disabled with "A project needs at least one environment" when only one exists). **Destroy** keeps the environment — its tooltip/confirm copy (`src/lib/environment-menu.ts`) says so. The settings gear had been removed earlier without a replacement; that was the gap.
- **Server** placement lives on the **Hosting** compose tab (`updateEnvironment({ serverId })` / project `options.defaultServerId`) — not compose YAML, and not at deploy time. Deploy stays disabled until a connected server is selected. Different environments may select different servers. Compose must not carry `x-turbopanel.placement` (instance validation rejects it; UI `stripComposePlacement` is an input-sanitization path only).
- `EnvironmentDetailSection` remains as a thin wrapper (heading + `EnvironmentDetailBody`) for embedded Environments-tab use.
- **Container status** is shown inline in the active environment's Containers panel (`ContainerStatusBadge`, Postgres-backed `fetchContainers({ serviceId })` per service — never DO reads), so no separate environment page is needed to see it. Live stdout/stderr is an on-demand tail (`GET /containers/:id/logs`, `useContainerLogTail`, `LogTranscriptView`) — never stored, never a fleet-wide explorer.
- **Managed engine versions:** operators pick a **version series** (`18`, `9.7`, `12.3`) plus a base-OS **variant** (Alpine / Debian / Oracle Linux 9 / UBI) — never a raw OCI tag. `src/lib/managed-releases.ts` mirrors the control-plane catalog (`turbopanel/src/features/managed/releases.ts`); `MANAGED_SERVICE_CATALOG` `defaultImage` / `allowedImages` derive from it, and `managed-releases.test.ts` pins the literal set. `ManagedVersionPicker` (`managed/managed-version-picker.tsx`) is the **only** place a series is chosen: it appears on the managed setup panel and sends `engineSeries` / `imageVariant`. A cluster's series is immutable afterwards (**409** `managed_series_immutable`), so the Settings panel's base-image picker offers only other variants of the running series (`managedVariantImagesForImage`); for PostgreSQL the control plane also refuses an Alpine <-> Debian swap (**409** `managed_variant_swap_unsafe`, text indexes would break), and the picker still offers it, so the refusal surfaces through `managedErrorMessage` and the Status header shows `PostgreSQL 18 · Alpine` from `detail.release` (`managedReleaseSummary`). Adding a series is a three-repo change — control-plane catalog, daemon allowlist, this mirror.
- **Managed external access:** one yes/no per **server**, "Allow external access to the databases on this server" (default No), not a per-cluster scope menu. No = only services on that server connect (sites run by a site owner's Linux user on `127.0.0.1`, containers bound to the cluster over the managed Docker network); Yes = the database ports are open on all of the server's addresses and the firewall decides who reaches them. `ManagedExternalAccessSwitch` (`managed/managed-external-access-switch.tsx`) is the only control: the create form (`ManagedSetupPanel`) saves it through `saveServerManagedExternalAccess` before create and only when it changed; `ManagedSettingsPanel` shows one row per server in `detail.externalAccess.servers[]` and saves on press, outside the cluster Apply. Always show the plain warning when `otherClusters > 0` (the switch moves those too). Endpoints use `reach: 'local' | 'external'`; never show scope or network names.
- **Managed client TLS (SSL mode):** `src/lib/managed-ssl.ts` mirrors the control-plane policy (`turbopanel/src/features/managed/ssl.ts`) — six modes (`disable` → `verify-full`), platform fallback `require`, and pure helpers (`resolveManagedSslMode`, `managedSslRequiresTls`, `managedSslVerifiesServer`, `managedSslDsnParam`, `describeManagedSslPolicy`), pinned by `managed-ssl.test.ts`. It is a **client-facing** policy at the shared ProxySQL listener; the listener ↔ engine leg is always encrypted, so never present this as "turn on database TLS". `ManagedSettings.ssl` is `{ mode?: ManagedSslMode }` — **omitting `mode` is what keeps a service inheriting**, so the settings form must send `{}` rather than the resolved value. `ManagedSslModePicker` (`managed/managed-ssl-mode-picker.tsx`) is the only picker: it renders the inherit row only when given an `inheritLabel` (`managedSslInheritLabel(orgDefault)` → e.g. `Organization default (Require)`). Per-service selection lives in `ManagedSettingsPanel` (`organizationSslMode` comes from detail `ssl.organizationDefault`); org-wide default lives at `/<orgId>/managed/settings` (`ManagedDefaultsSettingsSection`, manage-gated), which invalidates `queryKeys.org(orgId).managed.all` on save because every managed detail response carries a resolved `ssl` block. The Connect panel renders the effective policy from `describeManagedSslPolicy` (DSN parameter · plaintext refused/allowed · which layer set it) and points at the org CA download when the mode verifies — never a hardcoded `sslmode=verify-full` line.
- **Managed listener ports:** `src/lib/managed-ingress-ports.ts` mirrors the control-plane contract (`turbopanel/src/features/managed/ingress-ports.ts`) — `postgres` / `mysqlFamily` (MariaDB rides the MySQL listener), platform defaults `15432` / `13306`, and the same rejections (`out_of_range` outside `1024`–`65535`, `reserved_admin` `6032` / `6132`, `reserved_private_range` `45000`–`45999`, `collision` when both families match), pinned by `managed-ingress-ports.test.ts`. `managed-services.ts` re-exports `managedIngressPortForEngine` — there must be exactly one implementation. Ports are **org-wide**, edited on `/<orgId>/managed/settings` as its own panel (blank field = inherit, via `parseManagedIngressPortInput`); there is no per-service port. Client-side validation is a courtesy — a **host** listener conflict is only detectable on the server, so a save can still fail from the daemon preflight. Never render a port from the platform constant when the API supplied one: the Connect panel prefers `connection.port` / `managed.port` and falls back to the default only before provisioning, since the effective port comes from the **server-owner** org.
- **Managed projects:** tabbed shell (`/overview`, `/connect`, `/data`, `/backups`, `/environments`) via `ManagedEnvironmentBody` focus panels — never Compose UI. **Overview** = cluster topology (replicas, promote); **Connect** = shared listener endpoints + CA download + service bindings; **Data** = credentials / users & databases. Create via empty project → setup → managed catalog; provisioning uses `createEnvironmentManaged` with show-once root password. **Members** ride `useEnvironmentManaged` + `useManagedStatus` (status polls only while `provisioning`/`applying`) — never a members-only timer; commands share one `COMMAND_POLL_MS` batch. **Backups** (`managed/managed-backups-panel.tsx`): **Back up now**; **Restore** behind typed confirmation (managed/project display name); **Delete** two-press. Metadata-only — no download endpoint. Project Settings tab removed; delete uses the shell trash control. Header trash / `ProjectDeletePanel` wait on `managed.destroy` (`deleteEnvironmentManaged`) before `DELETE /projects/:id` or `DELETE /environments/:id` — never tenant `environment.stop`. Compose delete lives on the **Settings** tab → Danger instead.


**The console reads the authored shape, and only the authored shape.** The instance compiler names its stages — `ComposeLayer[]` (authored) → `Application` → `ResolvedApplication` → `ServerDeployment` (`turbopanel/src/features/compose/ir.ts`) — but the editor, the visual service cards, the document lens, the topology diagram, and the `ui/src/lib/compose/*` lint and merge mirrors all read **stage one**: the `ComposeDocument` as an operator wrote it, plus the `x-turbopanel` blocks that document declares. Nothing in the console models the later three stages, and nothing should start to: placement, container names, slot addresses, release trees and `principal.id`s are compiler decisions the console *displays* (from live facts and from the Prepared preview) rather than derives. This naming pass changed no console behavior and no payload the console reads.
